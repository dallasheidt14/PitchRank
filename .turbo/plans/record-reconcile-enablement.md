# Plan: Controlled enablement of down-side record reconciliation (K≈0.7)

## Context

The down-side record reconciliation lever is built, unit-verified, and calibration-swept (scorecard `C:/PitchRank/.turbo/record-reconcile-sweep-scorecard.md`): at `RECORD_RECONCILE_DOWNPULL_K≈0.7` it moves the owner ground truth 7→11/23, cuts bubble teams 24→10 and losing-in-top-decile 422→278, lands 3 of 4 u16M over-ranking drops, and — uniquely — protects both the 63%-win ALBION and 90%-win SOLAR elites, with buried elites only mildly touched. It is committed **default-off** (`f1ee9231e`), so production is byte-identical today.

This plan turns it on in production, safely. Two hard facts shape it:

1. **The foundation is not in production.** `f1ee9231e` lives only on the local worktree branch `scf-off-staging` (`C:/pitchrank-scf-off`); it is not pushed and not on `origin/main`, which runs prod. Nothing can be enabled until the foundation merges to `main`. So Phase 0 ships the default-off foundation first.
2. **Merge and enablement are two separate approvals.** Merging the default-off foundation changes nothing live (audit trail: ship inert foundation → validate enablement → decide whether to flip on). Enabling is a distinct, later, separately-approved change.

Enablement uses the **workflow env-var** seam: the reconciliation dials are env-backed, so prod flips them by adding two lines to the rankings workflow (rollback = delete the two lines). The publish itself is gated on an automated stability check plus a **manual audit of key top cohorts**. Out of scope: Shell 2 / record-justified lift (explicitly excluded); the mediocre-record buried elites are not record-fixable and are not addressed here.

## Pattern Survey

### Analogous Features
- **`origin/main` `.github/workflows/calculate-rankings.yml`** — the prod publish workflow: Monday 12:30 UTC cron + `workflow_run` after Modular11 scrapes + `workflow_dispatch`. Runs `python scripts/calculate_rankings.py --ml --force-rebuild --engine glicko`. Its `env:` block sets **only** Supabase secrets — no engine-config env. `concurrency: ranking-calculation` serializes runs; a "Verify branch" step aborts non-dispatch triggers off `main`. This is the file the enablement env vars are added to, and the workflow a human dispatches to publish.
- **`origin/main` `scripts/calculate_rankings.py:141` `save_rankings_to_supabase()`** — the actual PUBLISH: upserts the board to `rankings_full` (load-bearing published table) and `current_rankings` via `_save_batch_with_retry` (`:386`), upsert-then-prune (`:519`) so the table is never empty. Entrypoint at `:744/:757` calls `compute_all_cohorts(use_glicko=True, --ml)` with persist defaults on.
- **Live-site read path** — frontend reads `rankings_full` via RPCs `get_national_rankings`/`get_state_rankings` (`frontend/app/api/rankings/national/route.ts:13`, `state/route.ts:23`), cohort page ISR `revalidate = 3600` (`frontend/app/rankings/[region]/[ageGroup]/[gender]/page.tsx:12`). "Published" = upsert to `rankings_full`; live within ~1h.
- **`[worktree] scripts/run_scf_off_staging.py`** — zero-prod-write board builder: `compute_all_cohorts(save_snapshot=False, persist_*=False, calculate_rank_changes_enabled=False)` → parquet + a named `LIKE rankings_full` scratch table; never touches `rankings_full`/`current_rankings`. Already carries `--record-reconcile {on,off}` + `--record-downpull-k` + `--record-beta/-r0/-win-weight`, `--fetch-snapshot`/`--games-snapshot`/`--today`, `--teardown`. This is the dry-run engine for Phases 1–2.

### Reusable Utilities
- **`[worktree] src/etl/glicko_config.py`** — env-backed reconciliation dials: `RECORD_RECONCILE_ENABLED` (`:173`, default `false`), `RECORD_RECONCILE_DOWNPULL_K` (default `1.0`), plus `_BETA=0.8`/`_R0=0.5`/`_WIN_WEIGHT=0.7`/`_GD_WEIGHT=0.3`/`_WIN_MIDPOINT`/`_WIN_SCALE`/`_GD_CLAMP`/`_TOLERANCE_FLOOR`/`_MIN_COHORT`/`_MIN_GAMES_FULL`. `__post_init__` (`:247`) **raises if `SOS_CREDIT_CAP_ENABLED` and `RECORD_RECONCILE_ENABLED` are both on**. The K≈0.7 config = only two env overrides needed (`RECORD_RECONCILE_ENABLED=true`, `RECORD_RECONCILE_DOWNPULL_K=0.7`); β/R0/win/gd already match the recommended defaults.
- **`[worktree] src/rankings/calculator.py:2050` `glicko_cfg = GlickoConfig()`** — the config-injection seam: `GlickoConfig()` constructed bare inside the prod compute path, so a workflow-level env var reaches the engine here. The cache fingerprint (`:2147`, keys `rr`/`rr_k`/…) already includes the reconciliation dials, so an enabled run gets a distinct cache (and `calculate_rankings.py` passes `--force-rebuild` anyway).
- **`[worktree] scripts/ranking_stability_check.py`** — the post-#885 before/after guard: compares two boards' `rank_in_cohort_final` for non-playing-team churn, mu→published stage shift, and top-N entry/exit; exits non-zero on FAIL. Supports `--compare-table`/`--baseline-table` (worktree refactor `_stage_shift(table_sql)` compares two arbitrary boards). Used as the automated gate in Phases 1 and 4.
- **`[worktree]` read-only scorers** (audit-gate inputs, all read a `--table` scratch table, write nothing): `data/staging/audit_ground_truth.py` (`--table`, `--elite-ceiling`; drop ≥ target, elite ≤15), `scripts/diagnose_bubble_teams.py` (`--rankings-table`; bubble count + attribution + review list), `data/staging/score_losing_top_decile.py` (`--table`; losing-in-top-decile count).

### Convention Anchors
- **Publish isolation** — staging never writes `rankings_full`/`current_rankings`; it writes parquet + a `LIKE rankings_full` scratch table keyed by `--table`. Prod writes the published tables only via `save_rankings_to_supabase`. Every dry-run/audit step in this plan runs against scratch tables.
- **Post-#885 safe-enable idiom** — flags ship OFF/conservative with dated rollback comments (`SCF_PUBLISH_ONLY`, `TIER_MULT_CENTERED` both bear "ROLLBACK 2026-06-15 … #885 scrambled standings … re-enable only behind scripts/ranking_stability_check.py"). Enablement is gated by the stability check plus a human audit.
- **Mutual exclusion, fail-closed** — reconciliation supersedes the SOS-credit cap; `glicko_config.py:247 __post_init__` and `run_scf_off_staging.py` both raise if both flags are on. Prod must keep `SOS_CREDIT_CAP_ENABLED` off (its default) while reconciliation is on.
- **Stacked default-off foundation** — `scf-off-staging` carries FOUR interdependent commits not on `main`, all default-off: `85e2c6a18` (SCF staging harness) → `4a66c34dd` (SCF-dial env-backing) → `5c4f44a3d` (SOS-credit cap, superseded prior art, kept default-off) → `f1ee9231e` (reconciliation). The reconciliation config's `__post_init__` references `SOS_CREDIT_CAP_ENABLED` (from `5c4f44a3d`) and the cache fingerprint builds on the cap's keys, so the stack cannot be cleanly split — Phase 0 merges all four (all default-off).

### Proposed Alignment
Merge the default-off stack to `main` behind one PR (byte-identical prod, verified by the flag-off unit suite + a flag-off staging board), then enable via the workflow env-var seam gated on the established `ranking_stability_check.py` + a manual top-cohort audit — matching the post-#885 precedent while using the env-backed design the foundation added. Keep merge and enablement as two PRs / two approvals.

## Implementation Steps

   - Open a PR `scf-off-staging` → `main` carrying the four default-off commits. PR body must state: all four flags (`SCF_*` unchanged at prod defaults, `SOS_CREDIT_CAP_ENABLED`, `RECORD_RECONCILE_ENABLED`) default OFF/unchanged → byte-identical prod; this PR ships inert foundation + dev tooling only, enablement is a separate later PR.
   - Reviewer confirms flag-off byte-identity for the whole stack: the engine unit suite passes, and `git show origin/main:src/etl/glicko_config.py` post-merge shows `RECORD_RECONCILE_ENABLED` default `false` and `SOS_CREDIT_CAP_ENABLED` default `false`. Note `SCF_ENABLED` becomes env-backed with default `true` and `SCF_FLOOR/DIVISOR` default `0.4/4.0` (prod values) — no SCF behavior change.
   - Merge is **user-gated** (per-PR approval). After merge, confirm `origin/main` contains `apply_record_score_reconciliation`, the `RECORD_RECONCILE_*` fields, the `rr_*` cache keys, and `run_scf_off_staging.py`.

2. **Phase 1 — Fresh zero-prod-write staging dry-run at K≈0.7 (reconfirm on current data)**
   - Run from the worktree checked out at the merged `MAIN_SHA` (Phase 0), with `C:/Python313/python` — the code under audit must be byte-for-byte what merged to prod. Fetch ONE fresh frozen snapshot pinned to the run date: `scripts/run_scf_off_staging.py --fetch-snapshot --games-snapshot data/staging/enablement_snapshot.parquet --today <YYYY-MM-DD>`.
   - Build a same-snapshot reconcile-OFF baseline (`--scf-mode on --record-reconcile off --table rr_enable_baseline`) and the reconcile-ON candidate (`--scf-mode on --record-reconcile on --record-downpull-k 0.7 --table rr_enable_k07`), both `--games-snapshot data/staging/enablement_snapshot.parquet --today <same date>`. Both are `save_snapshot=False` → zero prod-write.
   - Score `rr_enable_k07`: `data/staging/audit_ground_truth.py --table rr_enable_k07` (expect ~11/23, drops landed), `scripts/diagnose_bubble_teams.py --rankings-table rr_enable_k07` (bubble well below the baseline count), `data/staging/score_losing_top_decile.py --table rr_enable_k07` (below baseline). Confirm the scorecard's K≈0.7 signature reproduces on fresh data: ALBION ≤15, SOLAR ≤15, buried elites (Michigan/De Anza/Platinum) not materially below the `rr_enable_baseline` ranks.
   - **Hard pass/fail gate for Phase 1 is the scorer thresholds, NOT the stability script.** `scripts/ranking_stability_check.py --compare-table rr_enable_k07 --baseline-table rr_enable_baseline` runs in board-vs-board mode, which is **descriptive only — it emits INFO verdicts and never FAILs by design** (`ranking_stability_check.py:350`). Use its output (median |Δrank|, top movers, stage-shift delta, top-N composition) as *evidence for the manual audit*, not as an automated blocker. The Phase-1 gate is the concrete scorer bounds: GT ≈ 11/23 with the four u16M drops moved toward target, bubble and losing-decile strictly below the same-snapshot `rr_enable_baseline`, ALBION ≤ 15, SOLAR ≤ 15, and each buried elite (Michigan/De Anza/Platinum) no more than a small bounded tolerance below its `rr_enable_baseline` rank. If a hard *automated* stability gate is desired, that is a prerequisite tooling change (add explicit thresholds + FAIL to compare mode) — out of scope for this plan; do not rely on the current script to block.

3. **Phase 2 — Manual top-cohort audit gate (human sign-off before any prod write)**
   - A human reviews the `rr_enable_k07` scratch board for the key top cohorts — the two ground-truth cohorts (u16/Male, u17/Female) plus the other high-traffic top cohorts (e.g. the largest by team count / most-viewed: u15–u17 M/F, u19 M/F). For each, confirm on the scratch board: (a) the flagged over-ranked drops are demoted toward their targets; (b) genuine elites remain intact (no top-10 team with a strong record demoted); (c) buried elites are not driven materially below their reconcile-off rank; (d) **no rank cliff** — no large cluster of teams pinned at one identical reconciled score (spot-check `power_presos` vs `powerscore_core` deltas and the per-cohort score distribution).
   - This gate is a hard stop: proceed to Phase 3 only on explicit human approval. If any cohort fails, stop and either retune K in staging (repeat Phases 1–2) or abandon enablement — do not publish.

4. **Phase 3 — Enable in prod via workflow env var + publish (second approval)**
   - In a NEW PR (separate from Phase 0), add to the `env:` block of the **Calculate Rankings step** in `.github/workflows/calculate-rankings.yml` (the step whose env holds the Supabase secrets + `PYTHONUNBUFFERED` — NOT the separate scrape-preflight step's `GH_TOKEN` env) exactly two lines: `RECORD_RECONCILE_ENABLED: "true"` and `RECORD_RECONCILE_DOWNPULL_K: "0.7"`. Preserve every existing key in that block (Supabase secrets, `PYTHONUNBUFFERED`) and every other part of the workflow (the `schedule`/`workflow_run`/`workflow_dispatch` triggers, `concurrency`, the Verify-branch step, the run command). Do not set `SOS_CREDIT_CAP_ENABLED` (its default `false` keeps the mutual-exclusion guard satisfied); do not set β/R0/win (code defaults already match).
   - **Pre-enable seam check (fail-closed dependency):** `scripts/calculate_rankings.py:134-136` runs `load_dotenv(".env.local", override=True)`, and `.env.local` is tracked on `origin/main`. `override=True` makes any key that file defines win over the workflow env. It currently defines only `DATABASE_URL`/`SUPABASE_URL`/`SUPABASE_SERVICE_ROLE_KEY`, so the two reconciliation lines survive — but confirm before relying on the seam: `MSYS_NO_PATHCONV=1 git show origin/main:.env.local | grep RECORD_RECONCILE` must be empty. If `.env.local` ever defines a `RECORD_RECONCILE_*` key, the workflow env silently no-ops (publishes reconcile-OFF while appearing enabled — the project's dotenv override-order gotcha); set the dial in `.env.local` instead in that case.
   - Merge is **user-gated** (the second, separate approval). Merging only changes what the *next* rankings run computes — it does not itself publish.
   - **Publish-window guard (prevents an auto-triggered unaudited publish):** the workflow auto-runs on `main` via the Monday 12:30 UTC `schedule` cron AND `workflow_run` after the Modular11 scrapes complete. The instant the enablement lines land on `main`, any of those firing publishes a reconcile-ON board straight to `rankings_full` before the human dispatch (`concurrency` only serializes; it does not make the manual run first). So merge the enablement PR only **outside the Monday cron window and when no Modular11 scrape is in-progress or imminent**, then dispatch immediately (next bullets). Also note there is **no per-branch write isolation**: `save_rankings_to_supabase` writes the shared prod `rankings_full` on ANY run carrying the enablement lines — never do a pre-merge "test" `workflow_dispatch` on the feature branch, as it would publish reconcile-ON to prod.
   - **Immediately before publishing, pin the pre-enable baseline:** record `PREV_DATE` = the current latest reconcile-off board date (`SELECT max(snapshot_date) FROM ranking_history WHERE snapshot_date < current_date`). Phase 4 compares against this exact date.
   - **Publish by an immediate manual `workflow_dispatch` on `main` right after the enablement merge — do NOT wait for the next scheduled run.** Phases 1–2 validated a *same-snapshot* board; a later scheduled run computes on newer data and is no longer the audited configuration, breaking the audit chain. If any new scrape/games landed since the Phase-1 snapshot (or more than a short window has passed), re-run Phases 1–2 on a fresh snapshot and re-obtain manual sign-off before dispatching. The dispatched run executes `calculate_rankings.py --ml --force-rebuild --engine glicko` with the flag on → `save_rankings_to_supabase` upserts `rankings_full` + `current_rankings` (serialized by `concurrency: ranking-calculation`). Live site reflects it within ~1h (ISR) or a Vercel redeploy.

5. **Phase 4 — Post-publish verification + rollback path**
   - After the enabled run, verify the live board matches the audited staging expectation. Run the #885 countermeasure in its FAIL-capable **default** mode with the pinned baseline: `scripts/ranking_stability_check.py --prev-date <PREV_DATE>` (the date recorded in Phase 3). Passing `--prev-date` explicitly is required — the default resolver `max(snapshot_date) < current_date` (`ranking_stability_check.py:89`) can silently pick a same-day rerun instead of the true pre-enable board. This default mode DOES exit non-zero on excessive non-playing churn / stage-shift.
   - **Interpret a stability FAIL against expected reconciliation churn — the exit code alone is NOT the rollback trigger.** Down-side reconciliation *intentionally* demotes non-playing SOS-inflated teams (result-independent movement) — the same signal the #885 non-playing-churn check (`check_nonplaying_churn`, median-move > 30) was built to catch. So a FAIL may be the intended K=0.7 effect, not a regression. Compare observed churn to the scorecard's bounded expectation (bubble 24→10, losing-decile 422→278, and the same-snapshot median |Δrank| from the Phase-1 board). The PRIMARY Phase-4 evidence is that the live top cohorts match the audited staging board (drops landed, elites intact, no cliffs); roll back only if the live board diverges from the audited expectation or churn materially exceeds the scorecard bound — not on the raw exit code.
   - **Rollback (reversible, but not instant — quantify the SLA):** open a revert PR deleting the two env lines from the Calculate Rankings step (returns code default OFF), merge (user-gated), then dispatch the workflow. Time-to-recovery = revert-PR merge + a FULL ranking run (fetch games + `compute_all_cohorts` across all cohorts + upsert — tens of minutes) + up to ~1h of ISR staleness (`frontend/app/rankings/[region]/[ageGroup]/[gender]/page.tsx` `revalidate = 3600`) before the reconcile-off board clears the live site. To collapse the ISR window, **force a Vercel redeploy after the rollback republish completes**. No engine revert is needed — the flag lives in the workflow env.
   - Prod-safety recap: Phase 0 merge is inert (default-off); Phases 1–2 are zero prod-write (scratch tables only); Phase 3 is the only prod write, gated behind the stability check + manual audit + a separate PR approval; Phase 4 rollback is a two-line revert.
